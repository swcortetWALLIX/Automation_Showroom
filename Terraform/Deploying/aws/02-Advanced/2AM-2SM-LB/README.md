# WALLIX Access Manager and Bastion clusters behind load balancers on AWS

This example builds a complete lab in a new VPC: two Access Managers (AM) behind an Application Load Balancer, two Bastions (Session Managers, SM) behind a Network Load Balancer, and an optional Debian host used as an integration and jump host. Instance counts are configurable from 0 to 3. Passwords for the WALLIX service accounts are generated by Terraform and pushed with cloud-init.

The code is split into small modules under [modules/](modules/), each with its own README, so you can reuse them separately. It favours ease of use over hardening: treat it as a lab, and review it before using any part of it in production.

![Architecture](AWS_2AM-2SM-LB.drawio.png)

## What gets created

| Component | Details |
| --- | --- |
| Network | VPC (`vpc_cidr`), one AM and one SM subnet per instance (at least two of each, in different AZs), an Internet Gateway and a default route |
| Access Managers | `number-of-am` instances in private subnets, behind an internet-facing ALB (HTTPS with a self-signed certificate imported in ACM, HTTP redirected to HTTPS) |
| Bastions | `number-of-sm` instances in private subnets, behind an internal NLB forwarding SSH (22), RDP (3389) and HTTPS (443) |
| Debian host | Optional (`deploy-integration-debian`), with an Elastic IP, XFCE, xrdp and Firefox |
| SSH key | An ED25519 key pair generated by Terraform, registered as `key_pair_name` and written to `private_key.pem` |
| Local files | `private_key.pem`, and `info_replication.txt` when there are exactly two Bastions |

The WALLIX instances have no public IP. The ALB rejects some Access Manager paths (`/`, `/accounts/*`, `/configs/*`, `/appliance/*`, `/wabam/global*`) with a redirect to `/wabam/default`, so appliance and global configuration must be done on each instance directly, from inside the VPC.

## Prerequisites

* Terraform 1.9 or later and AWS credentials allowed to create VPC, EC2, ELB and ACM resources (see [../../README.md](../../README.md)).
* WALLIX images. With `ami-from-aws-marketplace = true` (default), the code looks for Marketplace AMIs named `bastion-<version>...aws` and `access-manager-<version>...aws`, so your account must be subscribed to the corresponding Marketplace offers. With `false`, it looks for images owned by WALLIX account `519101999238`; ask WALLIX support to share them with your account.
* If you deploy the Debian host: accept the [Debian 12 Marketplace terms](https://aws.amazon.com/marketplace/pp/prodview-g5rooj5oqzrw4) once for your account.
* A region with at least two availability zones (three if you deploy three instances of a kind).

## Deploy

```bash
cp lab.auto.tfvars.example lab.auto.tfvars
vi lab.auto.tfvars        # set allowed_ips, region, names, tags

terraform init
terraform apply
```

`lab.auto.tfvars` is loaded automatically because of its `.auto.tfvars` suffix. `*.tfvars` files are ignored by Git in this repository.

If you don't know your public IP, `curl https://ipv4.icanhazip.com` returns it (the `your-public_ip` output shows the same value after an apply).

### Inputs that matter

| Name | Why it matters |
| --- | --- |
| `allowed_ips` | Public CIDRs allowed on the ALB, the NLB and the Debian host (SSH, RDP). The VPC CIDR is always allowed on the load balancers. Use your own `/32`. |
| `project_name` | Prefix of most names. At most 17 characters, letters, digits and hyphens, because AWS load balancer and target group names are limited to 32 characters. |
| `key_pair_name` | Name of the key pair that Terraform creates. It must not exist yet in the region. |
| `bastion-version`, `access-manager-version` | Version prefix used to select the AMI. Empty means the most recent image. |
| `alb_internal`, `nlb_internal` | The ALB is internet-facing and the NLB internal by default. |
| `number-of-am`, `number-of-sm` | 0 to 3 each. |

The full list is in the [Reference](#reference) section.

## Connect

Sensitive outputs are hidden in the console. Read them one by one:

```bash
terraform output am_url_alb
terraform output debian_connect
terraform output -raw debianpassword_rdpuser
terraform output -raw sm_password_webui
```

**Debian host.** Connect with SSH as `admin` using `private_key.pem`, or with RDP as `rdpuser` and the password from `debianpassword_rdpuser`. The generated private key is copied to both users, so you can reach the WALLIX instances on their SSH administration port (2242) from there. Firefox is installed; with SSH you can also forward it with `ssh -X`.

**Access Manager.** Open `am_url_alb` from an address in `allowed_ips` (or from the Debian host). The certificate is self-signed for `<project_name>.lab`. For appliance configuration, browse the AM private IPs (`am_private_ip`) from the Debian host.

**Bastion.** The NLB is internal by default: use its name (`sm_fqdn_nlb`) or the private IPs (`sm_private_ip`) from the Debian host. The Bastion web UI `admin` password and the encryption passphrase are set at first boot by a cloud-init script; read them from `sm_password_webui` and `sm_password_crypto`.

**Service accounts.** `wabadmin`, `wabsuper` and `wabupgrade` passwords are in the `sm_password_*` and `am_password_*` outputs.

## Replication

With exactly two Bastions, Terraform writes `info_replication.txt` with both IPs, the generated passwords and the passphrase, in a format meant to feed the Bastion Master/Master replication setup. Replication itself is not automated here because the procedure depends on the Bastion version. The file holds cleartext secrets: delete it once replication is configured.

## Destroy

```bash
terraform destroy
```

This also deletes the generated key pair; the local `private_key.pem` and `info_replication.txt` are removed with it.

## Security notes

* Secrets (generated passwords, the SSH private key, the certificate key) are stored in cleartext in the Terraform state and in the two local files. Keep the state local or in an encrypted backend with restricted access.
* `allowed_ips` controls Internet access to the ALB, the NLB (when internet-facing) and the Debian host. `0.0.0.0/0` opens all of them; the `warning_allowed_ips_too_wild` output reminds you of it.
* The Debian host has a public IP and `rdpuser` has passwordless sudo.
* Inside the VPC, every subnet can reach the Access Managers on 80, 443 and 2242, and the Bastions on 22, 443, 2242 and 3389.
* The certificate on the ALB is self-signed. Replace it with an ACM certificate for a real domain if anyone else uses the lab.
* Root volumes are encrypted with the account's default EBS key.

## Cost

The main costs are the EC2 instances (four `t3.medium` plus the Debian host by default), the two load balancers and the Elastic IP. Run [infracost](https://www.infracost.io/) or the AWS Pricing Calculator for your region before leaving the lab running.

## Known issues

### Certificate import fails on the HTTPS listener

The creation of `aws_lb_listener.Frontend_AM` sometimes fails with a 403 error while attaching the ACM certificate. Create the listener manually in the console, import it, and apply again:

```bash
terraform import aws_lb_listener.Frontend_AM <listener-arn>
terraform apply
```

If you imported the port 80 listener by mistake, remove it from the state with `terraform state rm aws_lb_listener.Frontend_AM` and import the right ARN.

### The Debian host is unreachable from my IP

Check that `allowed_ips` contains your current public IP (output `your-public_ip`).
